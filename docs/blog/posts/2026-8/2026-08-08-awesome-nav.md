# 内容变多以后，为什么不把导航都写进 mkdocs.yml

站点刚开始只有少量页面时，把导航全部写在 `mkdocs.yml` 里很直接。但当 Python、AI、项目和日志继续拆分，配置文件会同时承担站点设置和所有内容目录，维护成本也会跟着上升。

<!-- more -->

## 集中配置的问题

一份很长的导航并不会立刻导致构建失败，真正的问题是改动范围越来越难判断：新增一篇 Python 文章，也要进入全站配置寻找正确的位置；目录中的文件与导航清单还可能逐渐失去同步。

对于持续增长的知识库，我更希望一个目录能够说明自己的顺序，而根配置只保留全站层级。

## 把职责交还给目录

这个站点使用 Awesome Nav 管理导航：

- 根目录的 `.nav.yml` 只定义首页、Python、AI、项目实践、工程实践、博客、日志和关于本站；
- 每个内容目录用自己的 `.nav.yml` 管理侧边栏名称与排序；
- `mkdocs.yml` 继续负责主题、插件、Markdown 扩展等全局能力。

例如，一个专题目录可以维护类似下面的结构：

```yaml
nav:
  - 概览: index.md
  - 语言核心: python-core.md
  - 标准库: standard-library.md
```

这样新增内容时，通常只需要修改离文章最近的配置。顶部导航保持稳定，侧边栏则可以随专题逐步展开。

## 需要接受的代价

分散配置并不是完全没有成本。查看完整导航时，需要在多个目录之间切换；文件移动以后，对应目录的配置也要一起更新。

因此我把它当作一种边界划分，而不是自动化魔法：全站结构由根目录负责，局部阅读顺序由内容目录负责。只要这条规则保持清楚，网站扩展时就不必让一份配置文件知道所有细节。
